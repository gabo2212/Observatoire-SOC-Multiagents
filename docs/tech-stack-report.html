Observatoire SOC — frontend and backend

Course project 420-VD2-ID. Two frontends sit on one Python backend: a Streamlit observatory on the GPU machine, and a static site on Vercel. The backend is six CrewAI roles, three tools, SQLite traces, and a local Qwen GGUF on llama-server.

React is not source code in this repo

You do not write React, Vue, Next.js, or an npm app. Streamlit's own browser client is a React app that the streamlit package ships, and it loads Plotly.js for charts. Your screens are Python calls (st.tabs, st.form, st.plotly_chart) plus dashboard/studio.css. The public site is HTML, CSS, assets/mark.js, and a short script in presentation.html.

How a mission crosses the two sides

Backend boxes run in Python. The last box is the Streamlit frontend, which only reads SQLite and live_status.json. Accent boxes are the six roles. Source: pipeline/crew_runner.py.

What SQLite does in this app

SQLite is the memory of the observatory. It is a single file, data/traces/observatory.db, opened by Python's built-in sqlite3 module. There is no database server, no Postgres, and no ORM. TraceStore in pipeline/tracing.py creates the file the first time a mission or the dashboard starts, then builds two tables if they are not already there.

SQLite is the history. The live pulse is a different file.

While a mission is running, the Lancer tab polls data/traces/live_status.json so the checklist can move. SQLite is written at the same moments, but the charts, the replay slider, the KPIs, and the run picker all read the database after each step is committed. Alert logs stay as JSON on disk. The GGUF is not stored here.

One mission, three writes

WhenCallWhat lands in the file
Before the first agentstart_runOne runs row, status running, with the scenario, mission text, and model name
After each of the six agentsadd_stepOne steps row: duration, tokens, tools, errors, quality, and the agent's text
After the rapporteurfinish_runThe same runs row is updated: success, partial, or failed, plus totals and the final brief

The run id looks like run_20261018T143022_ab12cd34. It is the primary key. Every step points back to it. A finished mission is one runs row and six steps rows. run_batch and the Streamlit launch button both go through SOCObservatoryCrew, so both write the same tables. Offline mode still writes them. The model being down does not skip the database.

runs — one row per mission

ColumnMeaning
run_idPrimary key. Timestamp plus 8 random hex characters
scenario, scenario_label, missionWhich case ran, and the French mission text
started_at, ended_atUTC ISO timestamps. ended_at is filled in finish_run
statusrunning, then success, partial, or failed
modelDisplay name of the local GGUF
total_duration_sSum of the six step durations
total_tokens_in, total_tokens_outPrompt and completion tokens, estimated when CrewAI does not return usage
total_cost_usdFrom those token counts. Defaults to 0 because inference is local
error_count, retry_countTool failures and the CrewAI-to-OpenAI fallback
quality_score0 to 0.98, from length and whether the brief mentions P1 or priority
final_resultThe rapporteur brief, the text shown in Analyser

steps — one row per agent

ColumnMeaning
id, run_id, step_indexAuto id, foreign key to runs, order 0 through 5
agent, task, statusRole key, task title, success or error
start_time, end_time, duration_sWall clock for that agent only
tokens_in, tokens_out, cost_usdThat step's share of the run totals
tools_used, tool_callsJSON text, for example parse_alert_log on the collecteur
retries, errorserrors is a JSON list of exception strings
messages_toJSON list of the next agent, the edge the Sankey draws
result_summaryFirst 500 characters, used in the replay
raw_outputFull reply, stored only up to 8000 characters
quality_scoreSame heuristic as the run, computed on this step's text

tools_used, errors, and messages_to are TEXT columns. get_steps runs json.loads on them before the dashboard sees the row. A broken JSON value becomes an empty list instead of crashing the page.

Who writes it, and who reads it

PieceRole
pipeline/tracing.pyTraceStore. Opens the file, creates tables, inserts, updates, lists, exports
pipeline/crew_runner.pyThe only writer during a mission: start_run, add_step, finish_run
pipeline/seed.pyIf runs is empty, copies data/traces/demo_runs.json in so the first dashboard open is not blank
dashboard/data_loader.pylist_runs and get_steps become pandas frames. Every chart and KPI starts here
dashboard/app.pyRun picker, replay, comparison, and the final brief all use those frames
scripts/export_traces.pyexport_json writes the whole database back out as demo-style JSON
scripts/run_batch.pyMany missions, same TraceStore, so Comparer has more than one run

Each call opens a connection, sets row_factory to sqlite3.Row, commits, and closes. There is no pool and no background writer. The dashboard never sends SQL of its own. It asks TraceStore for dicts, and pandas does the averages: success rate, mean duration, token sums, the most used agent, and the slowest agent.
